# 技术发现

部署过程中踩到的三个坑，按「现象 → 排查 → 根因 → 对策」记录，供复现与后续维护参考。

---

## 发现 1：模型给出的字符偏移不能直接采信

**现象**：模型输出的 `start_char` / `end_char` 语义上大致对，但经常偏几个字符，导致 `text[start:end] != quote`。

**排查**：对 336 个 span 做逐字符比对 —— 141 个（42%）偏移本来就精确，195 个偏移有偏差，其中 192 个能通过"在原文里搜 `quote`"救回，3 个 `quote` 本身在原文中不存在。

**根因**：模型是在字符级别"估计"位置，而不是真的在计数字符。这个能力对 1.5B 模型而言不稳。

**对策**：`src/spanfix.py` 的 `reanchor()` —— 拿模型给的 `quote` 在原文里定位，把偏移重写为真实位置，并把 `quote` 规范化成原文切片。解决率 0.9911（192/195）。注意实现时**必须先深拷贝输入**，否则会就地改掉调用方的对象（这个 bug 曾让"重锚定前后"指标完全相同，掩盖了效果）。

## 发现 2：QLoRA 适配器与 4-bit 底座强耦合（最重要）

**现象**：按标准流程「合并 LoRA → fp16 → 转 GGUF 量化」部署后，模型行为**退化为基座**：

| 输出特征 | 训练配置（4-bit + adapter） | 合并进 fp16 后 |
|---|---|---|
| 顶层键名 | `product_or_service` | `product_service`（错） |
| 证据数组 | 有 | **完全没有** |
| 状态枚举 | `known` 等 | `known`，但字段缺失 |

**排查**（四步排除法）：

1. **合并是否真的执行了？** 比对合并前后权重哈希：`layers.0.self_attn.q_proj` 从 `6e8bd877…` 变为 `54f66e1b…` —— 变了，合并确实生效。
2. **是不是 transformers / peft 版本问题？** 在 transformers 5.23 + peft 0.22 和 4.46.3 + peft 0.13.2 上分别复现，输出哈希完全一致 → 排除版本因素。
3. **adapter 本身是否训练过？** 直接读 `adapter_model.safetensors`：`lora_B` **100% 非零**（max 1.05e-2），初始化是全零，所以确实训练过。
4. **激活了吗？** `LoraLayer` 实例 196 个、`active_adapters=['default']`、`scaling=2.0`，且"开 adapter"与"关 adapter"的输出哈希不同 → 适配器是激活的。

**根因**：LoRA 的增量相对幅度只有 **1e-3 量级**（`||Δ||/||W||` 中位数 5.78e-3）。训练的底座是 **nf4 4-bit 量化后**的权重，增量学的是"相对量化噪声基座"的修正；换到干净的 fp16 底座上，参考系变了，修正方向失配。再经 Q4_K_M 量化（相对误差约 1e-2），增量被完全抹平。

**对策**：`tools/merge_into_dequant.py` —— 把适配器合并进**反量化后的 4-bit 权重**：

```python
W = bnb.functional.dequantize_4bit(wq.data, wq.quant_state).float()  # 必须带 quant_state
delta = (lora_B @ lora_A) * scaling
merged = (W + delta).half()
```

注意：`Params4bit.dequantize()` 直接调用会返回**半尺寸**张量（把两个 4-bit 当成一个 uint8 读），必须走 `bnb.functional.dequantize_4bit(data, quant_state)`。

合并后的模型（`merged4deq`）转 GGUF **Q8_0 后行为保真**，f16 与 Q8_0 输出一致。这条路径把单例耗时从 62–80 秒压到 20–36 秒。

## 发现 3：模型对提示词极度脆弱，约束应放在解码期

**现象**：为治"给商品名编造『未知商品』并附假证据"这个幻觉，在系统提示词后追加两条硬约束（禁止占位词、限制枚举取值）。

**结果**：通过率从 **2/5 掉到 0/5**；span 总数从 19 个掉到 2 个；字段开始缺失 `status`。

**根因**：提示词与训练时逐字节一致是模型进入正确分布的前提。任何追加都会把输入推出训练分布，1.5B 模型的鲁棒性不足以吸收这种偏移。

**对策**（两条并行）：

1. **解码期语法约束**：把 `schema/commitment_schema_v1.json` 通过 `response_format: {type: json_schema}` 交给 llama.cpp，在解码阶段就排除"自创字段 / 缺 required / 枚举越界"。结构类错误归零。
2. **确定性占位归一**（`server/app.py` 的 `normalize_placeholders()`）：模型用「未知商品」表达"原文没给名称"，把该字段归一为 `name=""` / `status=unknown` / `evidence=[]`。这不是掩饰幻觉——归一后该字段不再声明任何证据，而 schema 里 `unknown` 本来就不需要证据；反而消除了"为占位内容伪造 span"这一真实错误。

组合后：**11/12 通过，20–36 秒**。

## 副作用记录：两次静默失败的 `str.replace`

排查过程中有两处代码修改因为 `Python str.replace` 没匹配上而**静默无效**，且第一次的验证只检查了"目标字符串是否出现"，没有检查"旧字符串是否消失"，导致多跑了一轮无效部署。

教训（已落实到脚本）：

- 改完必须断言**旧特征已消失**，而不只是新特征出现；
- 长段落替换改用「标记切片重写」而不是整段字面量匹配；
- 涉及转义字符（`\n`）时改用 `chr(10)` 拼接，避免被多层 shell/JSON 转义吃掉。
